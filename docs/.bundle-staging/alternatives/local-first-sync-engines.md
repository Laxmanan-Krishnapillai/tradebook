# Local-First Sync Engines - PowerSync / ElectricSQL / TanStack DB / Zero / Replicache

*Part of [Alternative Architecture Exploration](README.md).*

### 7.2 Local-first sync engines over Postgres — PowerSync / ElectricSQL / Zero / Replicache

Server Postgres stays source of truth; sync engine mirrors relational data into local SQLite/WASM store in browser, giving genuinely zero-network-wait reads, writes reconciled in background. `.NET`/FastEndpoints keeps write authority; kanban cards and canvas nodes/edges become ordinary relational tables synced per board/workflow ID. **Closest real match to "buttery smooth, low latency, low memory" of anything researched** — rendering never waits on network at all, beats even §6.2 read-only-direct-to-SurrealDB pattern. Maturity: PowerSync most battle-tested option (Postgres and MongoDB both GA). ElectricSQL GA as of March 2025 but read-only — writes still go through your own API, fits this plan's write model exactly. Zero (Rocicorp) only reached 1.0 in June 2026, already shipped breaking permissions change, reportedly caps around 100GB. Replicache archived/EOL — don't adopt new. **Real cost: migrating off SurrealDB to Postgres and owning conflict resolution yourself** — none of these give free CRDTs. Not for teams unwilling to leave SurrealDB or needing its multi-model/graph query capabilities.

### 7.7 ElectricSQL — a deeper look

Postgres logical replication sole source of truth. Electric's sync service consumes WAL, serves **Shapes** — single table plus optional `WHERE` clause and column selection, *not* a join (aggregates, `now()`, full-text/JSONB operators unsupported in `WHERE` clause) — over genuinely plain HTTP protocol (offset-based cursors, long-polling for live updates, SSE fallback). Because offsets are cacheable resource identifiers, CDN can collapse thousands of clients polling same shape/offset into one origin request — Electric's real differentiator vs WebSocket-based competitors. Client storage store-agnostic (PGlite/WASM Postgres flagship option, but protocol client thin fetch/long-poll wrapper that can feed any store).

**Confirmed: Electric has no built-in write path, mutation API, or upload queue at all.** Read-path-only by design — writes go straight to your own backend, Electric only syncs resulting change back down via replication. Electric's own docs pair it explicitly with **TanStack DB (§7.8)** for write side; two-part stack, not single product.

**Authorization entirely manual, arguably heavier than PowerSync's Sync Rules.** Electric doesn't auto-enforce Postgres RLS on shapes — implement either "proxy auth" pattern (your API sets shape's table/WHERE/columns server-side) or "gatekeeper auth" pattern (token-issuing endpoint authorizes specific shape). Same class of risk as SurrealDB `PERMISSIONS` or PowerSync Sync Rules (§7.2), but raw HTTP, no rules DSL at all to structure it.

**Licensing confirmed Apache 2.0** — fully open source, more permissive than PowerSync's Fair Source License or SurrealDB's BSL. Self-hosting fully supported; managed Electric Cloud option also exists (Pro $249/mo, Scale $1,999/mo, free tier to 5M writes/mo, priced April 2026). **Confirmed Postgres 14+ hard requirement** — same "means leaving SurrealDB" constraint as PowerSync, not incremental addition.

**Maturity caveat worth tracking**: Electric hit 1.0 GA March 2025, shipped major storage-engine rewrite in v1.1 (Aug 2025, 100x+ write throughput after production load exposed bottlenecks). Since then company rebranded to "Electric" (electric.ax), visibly repositioned around "agents on sync" / Durable Streams (late 2025-2026) — roadmap-prioritization risk for teams betting on Postgres-sync product line specifically, even though still maintained.

**Read**: excellent at cheap, CDN-cacheable, low-latency partial Postgres replication; not whole-lift replacement on its own. Single-table-shape constraint pushes every relational join in app's domain model (kanban cards to tags, workflow nodes to edges) into client-side shape-stitching, auth burden real. Treat as one credible half of solution — paired with TanStack DB, plus hand-built auth proxy — not drop-in SurrealDB replacement.

### 7.8 TanStack DB — a deeper look, and a path that doesn't require leaving SurrealDB

TanStack DB is client-side reactive store built on top of TanStack Query: collections, live queries, optimistic mutations. **Confirmed: live-query engine runs on differential dataflow (via `d2ts`, TypeScript incremental-dataflow library), not query-rerun-on-change** — TanStack's own benchmark shows live query updating under 1ms even on 100k+ row in-memory collection. Concretely: join of workflow nodes to edges, or kanban cards to tags, becomes `useLiveQuery` SQL-like join across two normalized collections, recomputing only delta on each change. **Genuine capability upgrade over §6.11's hand-rolled pattern**, where join/aggregate computed in `useMemo` over TanStack Query cache gets recomputed from scratch on every push event, not incrementally.

**Collections abstraction confirmed pluggable — important part for this plan**: Query Collection wraps plain TanStack Query (any REST/GraphQL source — works with existing `.NET` backend unmodified), Electric Collection natively wraps Electric shapes (Postgres-only), official adapters also exist for PowerSync, TrailBase, RxDB, plus LocalOnly adapter for pure UI state. Critically, **community collection adapters already exist for Supabase and, notably, SurrealDB specifically** (`ForetagInc/tanstack-db-surrealdb`), wrapping SurrealDB's `LIVE` WebSocket stream directly — no Postgres or Electric involved at all.

**Optimistic mutations = built-in version of exactly pattern designed by hand in §6.11**: `insert`/`update`/`delete` write to optimistic overlay instantly, `onInsert`/`onUpdate`/`onDelete` handler persists to real backend, thrown error auto-rolls back, same-record mutations auto-merge. Assumes same design already adopted here — client-generated ID carried from optimistic write through server confirmation — drop-in upgrade to hand-rolled reconciliation code, not different idea requiring redesign.

**Maturity — genuinely early**: beta, v0.6.17, MIT license, ~3.8k GitHub stars. Built by two ex-ElectricSQL engineers under TanStack org (Tanner Linsley). No 1.0 yet; 0.1 launch explicitly solicited design partners, HN sentiment cautious ("wouldn't bet my app on the beta"). **Bundle cost real**: `@tanstack/db` core ~70KB min+gzip, 5-7x heavier than TanStack Query's core (~10-13KB), keeps normalized collections plus derived indexes resident in memory — genuine cost against stated "low memory" goal, not free upgrade.

**Additive path, confirmed without requiring §7.2/§7.7 Postgres migration**: Query Collection supports direct incremental writes (`writeInsert`/`writeUpdate`/`writeDelete`/`writeBatch` with `{refetch:false}`), so SurrealDB live-query push events can feed it without polling — or fully custom collection built following TanStack's documented WebSocket-sync pattern (begin/write/commit, buffer-before-ready, ack-then-drop-optimistic-state), exactly what `ForetagInc/tanstack-db-surrealdb` already does. **Either way, SurrealDB and `.NET` write authority stay completely untouched** — strictly additive frontend upgrade, not architecture change.

**Read**: worth adopting on own merits given app's real live-join/aggregate needs (kanban tags, workflow node/edge relationships, analytics aggregates), independent of Electric/Postgres decision entirely. Genuine upgrade over hand-rolled §6.11 pattern, not rebrand of it. But beta status plus bundle-size tax cuts against "low memory" — **pilot on one view (kanban board best candidate, given join-heavy tag/label model) before rolling out everywhere.**
