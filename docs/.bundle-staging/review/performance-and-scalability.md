# Performance & Scalability

*Part of the [architecture review](README.md).*

### 6.10 Performance architecture: what actually makes it feel "buttery smooth"

Team's stated priority — low latency, highly interactive, buttery smooth, low memory — checked against §6.2 network-topology debate directly. Finding: **network topology (direct vs. backend-relayed) is a minor lever for perceived smoothness; client-side rendering and write architecture is the dominant one.** Ranked by real-world impact, highest first:

1. **Optimistic updates on the user's own writes.** Single biggest lever. Doesn't shave a network hop, removes the wait entirely for the most latency-sensitive interaction there is: the user's own click/drag/edit. Implement this regardless of any other decision in this document.
2. **Selector-based state subscriptions and memoization** (Zustand slices, avoiding re-render storms). Unmemoized dashboards re-rendering large subtrees on every real-time tick cost tens of milliseconds of main-thread time per update — this dwarfs any network number and is the most common real-world cause of a dashboard *not* feeling smooth.
3. **Virtualization correctness** (`@tanstack/react-virtual`). Getting measurement, overscan, or dynamic row height wrong causes visible scroll jank and holds onto DOM/memory for rows that should be recycled — this directly undermines the "low memory" goal too, not just smoothness.
4. **Batching/coalescing rapid update bursts.** Without this, a high-frequency live-query feed turns into a re-render storm that defeats #2 even if the memoization itself is correct.
5. **Layout-thrash avoidance in animation** (transform/opacity only, no forced synchronous layout reads) — see §6.7.
6. **Network topology (direct vs. relayed).** Genuinely last. In a same-region deployment, a backend relay hop adds low single-digit milliseconds — below a single browser render frame (16ms) and smaller than ordinary last-mile jitter to the end user. This is an existence-proof, not a guess: Supabase Realtime and Firebase/Firestore both already relay every real-time update through a server process and are marketed specifically on low-latency "instant" updates. **Decide the §6.2 direct-vs-relay question on security/auditability grounds — it is not a performance-forced choice.**

**Local-first sync engines don't apply here without a database swap.** ElectricSQL, PowerSync, and Zero (Rocicorp) would beat both WebSocket topologies for perceived read latency (serving reads from an already-synced local store means zero network wait), but all three are built around Postgres logical replication (WAL) as their change-capture mechanism — none have a SurrealDB adapter today. Adopting one means Postgres becomes the system of record, which is a database swap, not a config change, and is out of scope unless the team wants to revisit the SurrealDB decision itself. The realistic path that keeps SurrealDB: `@tanstack/react-query`'s normalized cache + optimistic mutations (§6.6), with SurrealDB live queries used as an invalidation/delta signal rather than the sole rendering source.

**SurrealDB live queries have a real, documented scaling soft spot — independent of which topology is chosen.** No official per-subscription memory benchmark exists, but concrete signals point to live queries being resource-heavy at high fan-out: the live-query notification buffer had to be raised from 100 to 15,000 per connection because notifications backed up ([discussion](https://github.com/surrealdb/surrealdb/issues/2750)); there's a documented case of live-query events hanging the entire process ([#5068](https://github.com/surrealdb/surrealdb/issues/5068)); heavy aggregate queries have starved concurrent light updates for 8-24 seconds ([#7358](https://github.com/surrealdb/surrealdb/issues/7358)); some SDKs stream whole-table diffs with no server-side filter. Routing through a backend relay does not dodge this cost, it just relocates the same per-subscription load onto a process the team controls (and turns backend fan-out into its own live-query-heavy workload to manage). **Action item: load-test real concurrent live-query counts against the actual dashboard's expected subscription pattern before committing to either topology** — this affects the "low memory" goal directly and is currently unverified in either direction.
