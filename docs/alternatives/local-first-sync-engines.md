# Local-First Sync Engines - PowerSync / ElectricSQL / TanStack DB / Zero / Replicache

*Part of [Alternative Architecture Exploration](README.md).*

### 7.2 Local-first sync engines over Postgres — PowerSync / ElectricSQL / Zero / Replicache

Server Postgres stays the source of truth; a sync engine mirrors relational data into a local SQLite/WASM store in the browser, giving genuinely zero-network-wait reads, with writes reconciled in the background. `.NET`/FastEndpoints keeps write authority; kanban cards and canvas nodes/edges become ordinary relational tables synced per board/workflow ID. **This is the closest real match to "buttery smooth, low latency, low memory" of anything researched** — rendering never waits on the network at all, which beats even the §6.2 read-only-direct-to-SurrealDB pattern. Maturity: PowerSync is the most battle-tested option (Postgres and MongoDB both GA). ElectricSQL is GA as of March 2025 but read-only — writes still go through your own API, which fits this plan's write model exactly. Zero (Rocicorp) only reached 1.0 in June 2026, already shipped a breaking permissions change, and reportedly caps around 100GB. Replicache is archived/EOL — do not adopt it new. **The real cost is migrating off SurrealDB to Postgres and owning conflict resolution yourself** — none of these give free CRDTs. Not for teams unwilling to leave SurrealDB or that need its multi-model/graph query capabilities.

### 7.7 ElectricSQL — a deeper look

Postgres logical replication is the sole source of truth. Electric's sync service consumes the WAL and serves **Shapes** — a single table plus an optional `WHERE` clause and column selection, *not* a join (aggregates, `now()`, and full-text/JSONB operators are unsupported in the `WHERE` clause) — over a genuinely plain HTTP protocol (offset-based cursors, long-polling for live updates, SSE fallback). Because offsets are cacheable resource identifiers, a CDN can collapse thousands of clients polling the same shape/offset into one origin request — this is Electric's real differentiator versus WebSocket-based competitors. Client storage is store-agnostic (PGlite/WASM Postgres is the flagship option, but the protocol client is a thin fetch/long-poll wrapper that can feed any store).

**Confirmed: Electric has no built-in write path, mutation API, or upload queue at all.** It's read-path-only by design — writes go straight to your own backend, and Electric only syncs the resulting change back down via replication. Electric's own docs pair it explicitly with **TanStack DB (§7.8)** for the write side; this is a two-part stack, not a single product.

**Authorization is entirely manual, arguably heavier than PowerSync's Sync Rules.** Electric does not auto-enforce Postgres RLS on shapes — you implement either a "proxy auth" pattern (your API sets the shape's table/WHERE/columns server-side) or a "gatekeeper auth" pattern (a token-issuing endpoint authorizes a specific shape). Same class of risk as SurrealDB `PERMISSIONS` or PowerSync Sync Rules (§7.2), but with raw HTTP and no rules DSL at all to structure it.

**Licensing is confirmed Apache 2.0** — fully open source, more permissive than PowerSync's Fair Source License or SurrealDB's BSL. Self-hosting is fully supported; a managed Electric Cloud option also exists (Pro $249/mo, Scale $1,999/mo, free tier to 5M writes/mo, priced April 2026). **Confirmed Postgres 14+ hard requirement** — same "this means leaving SurrealDB" constraint as PowerSync, not an incremental addition.

**Maturity caveat worth tracking**: Electric hit 1.0 GA in March 2025 and shipped a major storage-engine rewrite in v1.1 (Aug 2025, 100x+ write throughput after production load exposed bottlenecks). Since then the company has rebranded to "Electric" (electric.ax) and visibly repositioned around "agents on sync" / Durable Streams (late 2025-2026) — a roadmap-prioritization risk for teams betting on the Postgres-sync product line specifically, even though it's still maintained.

**Read**: excellent at cheap, CDN-cacheable, low-latency partial Postgres replication; not a whole-lift replacement on its own. The single-table-shape constraint pushes every relational join in this app's domain model (kanban cards to tags, workflow nodes to edges) into client-side shape-stitching, and the auth burden is real. Treat it as one credible half of a solution — paired with TanStack DB, plus a hand-built auth proxy — not a drop-in SurrealDB replacement.

### 7.8 TanStack DB — a deeper look, and a path that doesn't require leaving SurrealDB

TanStack DB is a client-side reactive store built on top of TanStack Query: collections, live queries, optimistic mutations. **Confirmed: its live-query engine runs on differential dataflow (via `d2ts`, a TypeScript incremental-dataflow library), not query-rerun-on-change** — TanStack's own benchmark shows a live query updating in under 1ms even on a 100k+ row in-memory collection. Concretely: a join of workflow nodes to edges, or kanban cards to tags, becomes a `useLiveQuery` SQL-like join across two normalized collections, recomputing only the delta on each change. **This is a genuine capability upgrade over §6.11's hand-rolled pattern**, where a join/aggregate computed in a `useMemo` over a TanStack Query cache gets recomputed from scratch on every push event, not incrementally.

**The Collections abstraction is confirmed pluggable, and this is the important part for this plan**: a Query Collection wraps plain TanStack Query (any REST/GraphQL source — works with the existing `.NET` backend unmodified), an Electric Collection natively wraps Electric shapes (Postgres-only), and official adapters also exist for PowerSync, TrailBase, and RxDB, plus a LocalOnly adapter for pure UI state. Critically, **community collection adapters already exist for Supabase and, notably, SurrealDB specifically** (`ForetagInc/tanstack-db-surrealdb`), wrapping SurrealDB's `LIVE` WebSocket stream directly — no Postgres or Electric involved at all.

**Optimistic mutations are a built-in version of exactly the pattern designed by hand in §6.11**: `insert`/`update`/`delete` write to an optimistic overlay instantly, an `onInsert`/`onUpdate`/`onDelete` handler persists to the real backend, a thrown error auto-rolls back, and same-record mutations auto-merge. It assumes the same design already adopted here — a client-generated ID carried from optimistic write through server confirmation — so it's a drop-in upgrade to the hand-rolled reconciliation code, not a different idea requiring redesign.

**Maturity — genuinely early**: beta, v0.6.17, MIT license, ~3.8k GitHub stars. Built by two ex-ElectricSQL engineers under the TanStack org (Tanner Linsley). No 1.0 yet; the 0.1 launch explicitly solicited design partners, and HN sentiment is cautious ("wouldn't bet my app on the beta"). **Bundle cost is real**: `@tanstack/db` core is ~70KB min+gzip, 5-7x heavier than TanStack Query's core (~10-13KB), and it keeps normalized collections plus derived indexes resident in memory — a genuine cost against the stated "low memory" goal, not a free upgrade.

**The additive path, confirmed without requiring the §7.2/§7.7 Postgres migration**: the Query Collection supports direct incremental writes (`writeInsert`/`writeUpdate`/`writeDelete`/`writeBatch` with `{refetch:false}`), so SurrealDB live-query push events can feed it without polling — or a fully custom collection can be built following TanStack's documented WebSocket-sync pattern (begin/write/commit, buffer-before-ready, ack-then-drop-optimistic-state), which is exactly what `ForetagInc/tanstack-db-surrealdb` already does. **Either way, SurrealDB and the `.NET` write authority stay completely untouched** — this is a strictly additive frontend upgrade, not an architecture change.

**Read**: worth adopting on its own merits given this app's real live-join/aggregate needs (kanban tags, workflow node/edge relationships, analytics aggregates), independent of the Electric/Postgres decision entirely. It's a genuine upgrade over the hand-rolled §6.11 pattern, not a rebrand of it. But beta status plus the bundle-size tax cut against "low memory" — **pilot it on one view (the kanban board is the best candidate, given its join-heavy tag/label model) before rolling it out everywhere.**
